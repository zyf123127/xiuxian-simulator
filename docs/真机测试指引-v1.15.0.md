# v1.15.0 真机（TapTap）实测指引与判读表

- 目的：验证"按按钮很卡、经常毫无反应"四层根因修复在真实手机上的最终效果
- 上传包：[Release v1.15.0](https://github.com/zyf123127/xiuxian-simulator/releases/tag/v1.15.0) 的 `taptap_verify.zip`（TapTap 开发者后台 → 更新 H5 包）
- 测试：真机进游戏后正常玩几分钟（点底栏各按钮、寻仇、坊市、修炼弹层）

## 三重诊断读数（任意全屏截图必含其一）

1. **左下角 HUD**（9px 绿字，恒显）：`触N 消K 应Xms 峰Xms 帧龄X 活0/1 F帧号`
2. **浏览器标签标题**：`F帧号 活0/1 触N 消K 帧龄X`
3. 若发生 Rust panic：页面顶部自动展开红色 `[PANIC@JS]` 重入栈面板

字段含义：触=JS 收到的触摸事件数；消=Rust 消费的点击数；应=最近一次"触→消费"延迟；峰=本次会话最差延迟；帧龄=JS 帧时钟年龄（>1000ms 即帧泵死）；活=音频保活是否启动；F=Rust 帧号。

## 判读分流

| 读数 | 结论 | 下一步 |
|---|---|---|
| 消K 随点击增长、应<100ms、帧龄<100ms、画面跟手 | 根因链闭环，问题解决 | 关闭 |
| 活0 且帧龄经常破千 | 音频保活未生效（静音页被容器钳制） | 查 errlog 保活行；换 wake-lock 兜底；核对触摸手势路径 |
| 消K 不随点击涨 | 输入桥/启动死链路 | 看 errlog：`[诊断] 启动死`、`[PANIC]`、`已收到输入事件` 缺失即桥断 |
| 应>300ms 但帧龄正常 | 单帧过重（字体/纹理尖峰） | 用 ?dbg=1 读 G/U 帧增量定位 |

## 本版已修的四层根因（对照）

1. 帧路径 std Mutex/Instant → miniquad 事件壳 `already borrowed` 恐慌风暴（一击=实例死）
2. X5 启动死：`sounds::init` 的 decodeAudioData await 永不返回 → 音频协程懒加载（静音进游戏）
3. 弹层开着底栏全吞 → 关弹层并同击执行
4. 静音页 intensive throttling（0.9fps/游戏时间 4.5% 流速）→ 近无声音频保活（X5 探针实测代码路径可跑通；真机生效性待本表 `活1` 确认）
